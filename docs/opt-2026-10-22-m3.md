### Why gate8 beats direct here (8 vs 1)
1. Auto-observe replaces re-reading. A text-only model has no screenshot, so after every action it re-reads the tree,
   often several times with different query/max_depth args: direct spends 56% of its calls on reads (16.9/run), the same
   call repeated up to 4.3x per run. gate8 attaches the post-action tree (diffed) to the action result: reads drop to
   13.0/run (47%), actions rise 13.4 -> 15.4/run, max identical-call repeat 4.3 -> 3.2. With a 30-turn cap this is the
   difference between finishing a short task and not (ow04 Chrome font: gate8 2/2, direct 0/2; ow02/ow14 gate8 only).
2. Safety did not cost successes: og02 (export over an existing PDF) - gate refused the overwrite twice, the model then
   produced a safe result both seeds; direct failed both (no unsafe either, it never got that far).
3. More runs end by the agent (17 vs 7) instead of the cap, but 5 of those gate8 stops are premature DONEs.
Not because of: speed (gate8 is slower per run, 76 vs 61 s, gate_ms + bigger tool results) or the reviewer (below).

### Gate-side defects found in this data
- D1 reviewer is blind: 25 of 30 step reviews got a window text with **no element rows** - the gate's own pre-click
  re-read (`refresh`, tree_format "elements") and agent reads with tree_format elements/both store only the header text,
  so the reviewer sees "(tree is in structuredContent.elements ...)" and says right_target/useful unlikely (P 0.04-0.44).
  29/30 denies; at least 6 were the right step and the model abandoned it.
- D2 a step-deny repeats: same action re-sent after look_light is reviewed and denied again (ow16 Text CSV x3, ow23 x2).
- D3 focus heal never works (0/41): retry after bring_to_front hits the same foreground_unavailable (input focus is
  already inside the target, `focus_within_target=true`, WM active window is another).
- D4 vision-only advice to a text-only client: "confirm with a screenshot", "read with include_screenshot:true before
  aiming by x/y", "Here is a fresh screenshot" - and the gate captures ~10 screenshots/run that are dropped.
- D5 bench caveats (both runs): terminal for OS tasks opens in /data/workspace (setup `cd testDir` lost), sandbox HOME is
  /data/home while tasks say /home/user, files from earlier runs persist (og01 /data/home/Desktop/pre.pptx existed).

### Round 1 - the reviewer was blind; a doubted step looped (commit c046252)
Hypothesis: the step reviewer denies right steps because it sees no element rows (D1), and the model abandons them or
re-sends and gets denied again (D2). Fixing what it sees + letting a re-sent step through should remove the 6
"gate blocked a needed step" failures' cause without touching safety (risky effects never go through the step review;
they go through authz/risk_gate, unchanged).
Change: (a) `record_observation`: a read without tree_markdown (tree_format "elements": the gate's own pre-click
re-read, batch reads, or the agent's choice) keeps a flat `- [N] role "label" value="..."` rendering in the observation
text, so the reviewer and dialog/risk text checks see the window (Element gains `value`). (b) step review: a signature
the reviewer doubted (look_light) that the agent re-sends after the fresh look runs once (`reviewer_insist`;
GUI_GATE_STEP_INSIST=0 off); tier "rule" reviews (possible-loop rule) are not affected. Fake driver now drops markdown
for tree_format elements like cua-driver (this exposed that `run_actions` read steps had relied on it).
Offline effect (r1_review.py over all gate logs): m3 step reviews 30, of which 25 had no element rows - all 25 came
from elements-format reads -> fixed by construction (0 left). Refusals removed by insist: 4 in m3 (og04 dir1, ow16
Text CSV, ow23 file name, ow23 PNG) - each a model turn; older logs 2 (0.9.1/0.9.4, did not log what the reviewer saw).
Not measurable offline: how the reviewer decides with rows (needs the reviewer LLM -> not called offline).
Safety audit unchanged (step review is not on the risk path). Tests: cargo 53+3 ignored, python 85.

### Round 2 - stall notes for a text-only model (commit below)
Hypothesis: m3 burns turns re-reading for content the tree cannot show: 27% of its reads are queries, 197 reads
returned a partial spreadsheet grid, terminals never show output; 3+ reads in a row = 25-29% of reads (ds41: 12-14%).
A one-time, cause-specific note at the first such read plus a stall note every 3rd read in a row should move those
turns to actions. Change: `--text-only` / GUI_GATE_TEXT_ONLY=1 (new cfg.text_only); in text-only gate mode a read that
shows a partial cell grid gets HINT_GRID (keyboard navigation, the result names the focused cell), a read of a terminal
window gets HINT_TERMINAL (output is not exposed; check the effect elsewhere or finish) - once per window; every 3rd
get_window_state in a row after the first action gets a stall note (all gate modes; GUI_GATE_STALL_HINTS=0 off).
Log events read_hint / streak_hint.
Offline (r2_stall.py, simulated on transcripts): m3 gate8 - notes fire in 48/68 runs (grid 33, terminal 13, stall 40),
first note at call #3 (median), only 2 of the 8 successful runs see any note; reads made after the note for the same
cause: grid 107, terminal 15 (~1.8 turns/run the notes target). ds41 (vision, text-only off): only the stall note,
7 / 4 fires in 36 / 34 runs. Effect on success not measurable offline.
(round 2 commit 0e97872)

### Round 3 - text-only sessions stop paying for and talking about screenshots (commit below)
Hypothesis: with a text-only client every screenshot is wasted (capture + JPEG re-encode, dropped by Pi), and advice
like "confirm with a screenshot" / "read with include_screenshot:true before aiming by x/y" / "Here is a fresh
screenshot, re-aim your x/y" sends a model that cannot see into pixel aiming or extra reads.
Change (cfg.text_only, all policies so direct and gate8 stay comparable): get_window_state never captures (an explicit
include_screenshot:true gets a one-line note); auto-observe never captures, a PARTIAL TREE no longer switches the app to
pixel mode; look_full in text-only = fresh tree attached, wording without screenshots; "No screenshot frame" after an
x/y click -> "aim with an element_token from the tree below" + fresh tree instead of a screenshot; the driver's
"confirm with a screenshot" is rewritten to "confirm from the tree".
Offline (r3_textonly.py, m3 logs): reads with a screenshot 731 (direct) / 713 (gate8), median 345/475 ms vs 272/388 ms
tree-only -> ~0.8-0.9 s/run of read time, 14-15 s of re-encoding and ~60 MB JPEG per condition that the client dropped.
Vision advice removed per run: gate8 "confirm with a screenshot" 8.7, "include_screenshot:true" 6.0, "fresh screenshot"
0.6, x/y-from-image 0.2 (direct 7.3 / 0.2 / 0.1 / 0.1). Small time gain; the point is no misleading instructions.
