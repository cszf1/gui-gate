# MCP 2026-07-28（逐请求 `_meta`）支持

## 问题

附带的 Cua Driver 0.38.0 实现了 MCP 2026-07-28（cua `libs/cua-driver/rust/crates/cua-driver-core/src/mcp_wire.rs`，`ProtocolSession`）：

- 请求的 `params._meta` 里没有 `io.modelcontextprotocol/protocolVersion` / `clientCapabilities` 就算“老式”；
  同一连接上没有先来一次老式 `initialize`，老式请求一律被拒（-32602 "Missing required per-request MCP metadata"）。
- `server/discover` 返回 `supportedVersions: ["2026-07-28"]`；新式结果带 `resultType: "complete"` 和 `_meta` 里的 serverInfo。

旧的 gui-gate 只转发客户端的 `initialize`，自己构造的 `tools/call` 不带 `_meta`。新式客户端（不发 `initialize`）的
`tools/list` 能用，但所有动作都被驱动拒掉；`server/discover` 原样转发，宣称支持 2026-07-28 却没有门的说明。

## 现在的做法（gui-gate 自己终结新式协议）

1. 驱动启动后（以及每次重启后）gui-gate 自己发老式 `initialize` + `notifications/initialized`，并缓存结果。
   所以 gui-gate 发给驱动的请求永远合法，和客户端用哪种协议无关。
2. 客户端的 `initialize` 由 gui-gate 用缓存回答（追加门的说明、gui-gate serverInfo），不再给驱动发第二次。
   万一握手失败（没有缓存），退回旧行为：转发客户端的 `initialize`。
3. 新式请求先由 gui-gate 按 2026-07-28 规则校验（版本不对 -32022 并给出 `supported`；缺 clientCapabilities -32602），
   转发前去掉 `_meta` 里的两个新式键，驱动只看到老式请求；gui-gate 内部发的请求不带客户端的 `_meta`。
   这样旧驱动（0.38 以前）也能服务新式客户端。
4. `server/discover` 由 gui-gate 回答：`supportedVersions` 只列 gui-gate 端到端处理的版本（`2026-07-28`），
   `instructions` 与 `initialize` 相同，`capabilities` 取自驱动的 initialize。
5. 新式请求的所有结果（转发的、`tools/list`、门自己合成的拒绝/报告等）都加 `resultType: "complete"` 和
   `_meta["io.modelcontextprotocol/serverInfo"] = gui-gate`；`*/list`、`*/read`、`server/discover` 另加 `ttlMs: 0`、`cacheScope: "private"`。
   新式客户端的 `clientCapabilities.elicitation` 按每个请求更新（决定能否向人提问）。

测试：`tests/fake_driver.py` 默认按 0.38 的 ProtocolSession 规则拒绝（`FAKE_PRE_038=1` 模拟旧驱动）；
`tests/test_mcp_meta.py` 覆盖新式客户端、老式客户端、驱动重启、`server/discover`、版本不对、旧驱动。

未做：gui-gate 发给客户端的请求（`elicitation/create`）仍是老式格式。
