# MCP 2026-07-28（逐请求 `_meta`）支持

## 问题

附带的 Cua Driver 0.38.0 实现了 MCP 2026-07-28（cua `libs/cua-driver/rust/crates/cua-driver-core/src/mcp_wire.rs`，`ProtocolSession`）：

- 请求的 `params._meta` 里没有 `io.modelcontextprotocol/protocolVersion` / `clientCapabilities` 就算“老式”；
  同一连接上没有先来一次老式 `initialize`，老式请求一律被拒（-32602 "Missing required per-request MCP metadata"）。
- `server/discover` 返回 `supportedVersions: ["2026-07-28"]`；新式结果带 `resultType: "complete"` 和 `_meta` 里的 serverInfo。

旧的 gui-gate 只转发客户端的 `initialize`，自己构造的 `tools/call` 不带 `_meta`。新式客户端（不发 `initialize`）的
`tools/list` 能用，但所有动作都被驱动拒掉；`server/discover` 原样转发，宣称支持 2026-07-28 却没有门的说明。

## 现在的做法（gui-gate 自己终结新式协议）

1. 驱动启动后（以及每次重启后）gui-gate 自己发老式 `initialize` + `notifications/initialized`，并缓存结果。
   所以 gui-gate 发给驱动的请求永远合法，和客户端用哪种协议无关。
2. 客户端的 `initialize` 由 gui-gate 用缓存回答（追加门的说明、gui-gate serverInfo），不再给驱动发第二次。
   万一握手失败（没有缓存），退回旧行为：转发客户端的 `initialize`。
3. 新式请求先由 gui-gate 按 2026-07-28 规则校验（版本不对 -32022 并给出 `supported`；缺 clientCapabilities -32602），
   转发前去掉 `_meta` 里的两个新式键，驱动只看到老式请求；gui-gate 内部发的请求不带客户端的 `_meta`。
   这样旧驱动（0.38 以前）也能服务新式客户端。
4. `server/discover` 由 gui-gate 回答：`supportedVersions` 只列 gui-gate 端到端处理的版本（`2026-07-28`），
   `instructions` 与 `initialize` 相同，`capabilities` 取自驱动的 initialize。
5. 新式请求的所有结果（转发的、`tools/list`、门自己合成的拒绝/报告等）都加 `resultType: "complete"` 和
   `_meta["io.modelcontextprotocol/serverInfo"] = gui-gate`；`*/list`、`*/read`、`server/discover` 另加 `ttlMs: 0`、`cacheScope: "private"`。
   新式客户端的 `clientCapabilities.elicitation` 按每个请求更新（决定能否向人提问）。

测试：`tests/fake_driver.py` 默认按 0.38 的 ProtocolSession 规则拒绝（`FAKE_PRE_038=1` 模拟旧驱动）；
`tests/test_mcp_meta.py` 覆盖新式客户端、老式客户端、驱动重启、`server/discover`、版本不对、旧驱动。

## 问人（MRTR，分支 desktop-human）

2026-07-28 规定服务端请求必须走 Multi Round-Trip Requests。新式客户端（请求带 2026-07-28 `_meta` 且 clientCapabilities 声明 `elicitation`）
需要人时，gui-gate 不再发服务端请求，而是让这次 `tools/call` 直接返回：

```json
{"resultType": "input_required",
 "inputRequests": {"human": {"method": "elicitation/create", "params": {"mode": "form", "message": "...",
     "requestedSchema": {...}, "_meta": {"io.github.cszf1/gui-gate": {"kind": "approve", "timeout_s": 120,
     "deadline_ms": 0, "tool": "click", "target": "Delete file", "reason": "...", "decision": "ask_human"}}}}},
 "requestState": "gg1.<instance>.<nonce>.<HMAC>"}
```

客户端问完人，用新 id 重发同一 `tools/call`，带 `inputResponses: {"human": ElicitResult}` 和原样 `requestState`。

- `requestState`（0.10.1 起 `gg1.<instance>.<nonce>.<HMAC>`，按门进程签名，见 docs/security-model.md）是 gate 内存里待答记录的 id：一次性（用过即删，也包括绑定对不上的那次尝试），绑定工具名 + 参数
  （去掉 gate_ack/gate_confirm 等，这两个参数本身也被丢弃，不能批准任何东西），对不上、伪造或重放回 JSON-RPC 错误 -32602；
  超过 `human_timeout + 5 s` 才回来的答案按超时（拒绝）处理；门重启后所有待答记录失效。
- 回答还绑定**提问时的结构化效果**（`_meta[...].effect`：工具、危险类型、资源、应用、窗口、载荷摘要）。客户端重试时门按当前状态
  重建效果；变了（例如终端里 Enter 要提交的那一行变了、窗口变了）就不使用这个回答，而是再发一次 `input_required`
  （`_meta[...].asked_again`），新的 requestState 绑定新的效果。
- 人的批准只换来**一次**派发许可，绑定最终参数的签名和效果（见 docs/security-model.md），用完即失效。
- 四种表单：approve `{decision: allow|deny}`（也接受老的 `{allow: bool}`）、answer `{answer}`（有选项时另加 `choice`）、takeover `{done: bool}`、
  ask_help `{choice: did_it|hint|try_other, note}`。只有 `action: accept` 且内容为肯定才算同意，其余（decline、cancel、超时）都是拒绝。
  结束原因记在结果的 `structuredContent.human_outcome` 和日志事件 `human_outcome` 里：`accepted | denied | declined | cancelled |
  timeout | window_closed | channel_unavailable | unattended | no_response`。
- `run_actions` 批量里遇到要问人的步骤：批量停在该步，提示 agent 单独发这一步（否则重试会把前面的步骤再跑一遍）。
- 客户端没声明 elicitation：不问人（桌面版里等于拒绝，`human_outcome: channel_unavailable`），从不放行；也没有让 agent 自己带确认码重试的路径。
- 老式客户端（initialize 声明 elicitation）仍收到老格式服务端请求，表单同上（approve 用老的布尔表单）。

测试：`tests/test_actions_e2e.py`（新式客户端，覆盖门的全部返回动作和四种问人）。

## 结果状态与上下文差分（分支 fix-security）

- 工具结果的 `structuredContent.status`：`executed | blocked | partial | done | unknown | input_required | done_by_person`（0.10.1 起，见下）。
  `unknown`：驱动在动作途中退出、超时或返回无法解析的结果，门不知道动作是否已经发生；门**不会**重发，同一动作下次发来时门先读窗口
  再重新决策。批量里出现时批量停下，`batch.unknown_step` 给出步骤号。`input_required`：需要人（批量里要单独发的步骤、无法联系人时的接管、
  `request_human` 没有通道）；与 MRTR 协议层的 `resultType: "input_required"` 不同。
- 动作后的自动观察在 `structuredContent.diff` 里给出结构化差分：`{base_snapshot_id, snapshot_id, window, full, rows_total,
  changed: [{line, text}], removed: [text], reordered: [{line, base_line, text}], truncated?}`。客户端持有 base_snapshot_id 那棵树时：
  删掉 removed，把 changed / reordered 放到各自的行号，其余行按基底顺序填入，结果就是当前完整树（rows_total 行）。
  门不知道客户端的基底（第一次看这个窗口、新开了窗口/对话框、变化太多、上次发送被截断）时 `full: true`、`base_snapshot_id: null`，
  文本里是完整树。文本部分仍只列变化的行（带父行）。

## v0.10.1：桌面客户端接口

### 客户端专用工具：`gate_next_step`、`gate_reset`

两者**不出现在 `tools/list` 里**（模型看不到），客户端直接 `tools/call`。客户端可在请求 `_meta` 里标
`"io.github.cszf1/gui-gate/client": true`（或 `_meta["io.github.cszf1/gui-gate"].client_only = true`）；不标也能用
（只记一条 `client_tool_unmarked` 日志），因为对模型无害：一个只给建议，一个只作废状态。

| 工具 | 输入 | 输出 `structuredContent` |
|---|---|---|
| `gate_next_step` | `window_id`（可选；不给就用最近观察过的窗口） | `observe`：`none \| tree \| tree+screenshot`；`extra_reason`：bool；`option`（价值模型选的选项）；`p_direct`；`reason`；`decision_id`（`ns-…`，日志 `next_step` 用同一个 id）；`advisory: true` |
| `gate_reset` | 无 | `reset: true`、`permits_cleared`、`pending_cleared`（作废的待答问人请求）、`observations_cleared` |

`gate_next_step` 在客户端下一次模型调用**之前**问：要不要先附新树 / 树 + 截图、要不要多想一次。只是建议，不授权任何东西。
`gate_reset` 在客户端停止或重启 agent 时调用：许可、批准、待答请求、观察缓存和快照 id 全部作废（拒绝记录和任务保留）。

### 真实 token 用量：`_meta["gui_pi/usage"]`

客户端在每个 `tools/call` 的 `params._meta` 里带产生这次调用的那条模型消息的真实用量：

```json
"_meta": {"gui_pi/usage": {"input": 5321, "output": 212, "cache_read": 4096, "same_message": false}}
```

`input`、`output`、`cache_read` 是 token 数（非负数，缺省为 0）。同一条模型消息发出多个工具调用时，只有第一个带这条消息的用量，
其余带 0 和 `same_message: true`，所以把所有调用加起来就是真实总量。门每次记一条日志 `usage`，在 `gate_report.model_usage`
里累计（`calls`、`messages`），`gui-gate costs` 用它给交回模型的选项计 token 代价。不带时 token 只能按截图像素估计。

### 问人请求的 `_meta["io.github.cszf1/gui-gate"]`

在已有的 `kind`、`timeout_s`、`deadline_ms`、`tool`、`target`、`reason`、`decision`、`effect`、`asked_again` 之外，按类型补充：

| 类型（`kind`） | 字段 |
|---|---|
| `approve` | `object`（门确认的具体对象：效果资源去掉前缀，没有就是目标）、`scope`（“这一个动作、这个目标、一次；目标/窗口/内容变了会再问”）、`consequence`（允许后的后果，按危险类型）、`target`、`effect: {tool, hazard, resources, app, window, payload}` |
| `answer`（澄清，`request_human`） | `options: [{label, value, effect}]`（2–4 个，给了或能从问题里读出时才有；`effect` 是“选它之后会怎样”，可能为空）+ `allow_other: true`（人仍可自己输入回答）；表单多一个 `choice` 枚举 |
| `ask_help`（求助） | `tried: [...]`：会话最近几步和门自己的尝试轨迹（`gate: …`） |
| `takeover` | `steps: [...]`：人要做的最少步骤（原因、“在应用窗口里自己做”、“然后在这里确认；门重读窗口，从不重做这一步”） |

客户端读这些字段时应宽容：缺什么就不显示，从不编造。

### 结果状态与 `next_action`

`structuredContent.status` 现在是 `executed | blocked | partial | done | unknown | input_required | done_by_person`：

- `done_by_person`：接管 `{done: true}` 或求助 `{choice: did_it}`，人自己做了这一步。门**没有**执行原动作，也不会再发；结果附带重读的窗口。
  客户端/模型不应重发这一步。
- 被 `extra_reason` 拦下时 `status: "blocked"`、`gate.decision: "extra_reason"`、`next_action: "rethink"`、
  `reasoning_budget_tokens: 1024`：不提供新观察，让同一个模型多想一次再发它决定的步骤；这一步照常过门，重想不授权任何东西。
- 结果里的 `human_outcome` 新增 `not_asked_again`：同一个效果（或同一问题）在同一任务版本里已经问过且没得到回答，这次不再弹出，按拒绝处理。

测试：`tests/test_remaining.py`（客户端工具不列出且不标也能用、next_step 只是建议并记日志、reset 作废许可/token/待答请求、
rethink、旧进程的 requestState、回答不等于批准、done_by_person 不重做、不再问、澄清选项、问人元数据、求助列出尝试、usage 记日志并累计）。
